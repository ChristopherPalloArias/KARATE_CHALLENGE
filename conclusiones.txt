============ HALLAZGOS Y CONCLUSIONES DEL EJERCICIO E2E DE PETSTORE ============

A traves del desarrollo y la incursion con el framework Karate DSL contra la arquitectura publica de la API REST de PetStore (Swagger), se definen las siguientes conclusiones del proyecto:

1. IDEMPOTENCIA Y COLISIONES EN ENTORNOS PUBLICOS COMPARTIDOS
   Hallazgo: Al someter la API de petstore.swagger a ejecuciones continuas con identificadores (IDs) manuales o repetitivos mediante POST, incrementamos drasticamente el riesgo de encontrarnos con solapamiento de informacion creada por otras personas a nivel mundial estudiando el mismo swagger.
   Conclusion: La mejor estrategia es delegar en la Maquina Virtual de Java del motor de pruebas la generacion de un ID criptograficamente unico o por timestamp puro de 8 caracteres (Math / System.currentTimeMillis() de Java embebido) concatenado con un sufijo seguro, asegurando una pureza continua al correr la bateria sin depender de metodos engorrosos de CLEANUP o Delete.

2. ENRUTAMIENTO Y MANEJO DE ESTADOS DE ESCENARIO EN KARATE
   Hallazgo: El framework Karate DSL aisla de forma muy estricta el estado (Variables, Response) en memoria. Al realizar un flujo tan dependiente y concatenado (Crear -> Leer -> Actualizar -> Flitrar), intentar separar cada accion en un bloque Gherkin "Scenario:" distinto arrojo errores de ReferenceError de Javascript.
   Conclusion: La definicion de arquitecturas E2E para pruebas API con variables secuenciales en Karate debe resolverse y empaquetarse logicamente dentro de un solo gran "Scenario:". Las buenas practicas de este lenguaje favorecen escenarios complejos donde el pipeline envia y recibe informacion (como recuperar un petId de Step A hacia el Step B).
   
3. BUGS LOCALIZADOS DE COMPORTAMIENTO INESTABLE EN EL SERVIDOR (500 VS 404)
   Hallazgo: En validaciones Edge o Casos Negativos, al apuntar intencionalmente al endpoint HTTP GET de recuperacion utilizando un ID aleatorio o excesivamente irreal (ej: 999888777), en multiples ocasiones el servidor de PetStore caia en fallo irrecuperable de backend arrojando codigo 500 Server Error ocultando la capa logica 404 Not Found.
   Conclusion: Esta volatilidad fue gestionada implementando un patron asertivo condicional dentro de Karate (Then match responseStatus == 404 || responseStatus == 500) favoreciendo una validacion grangem-degradada que impidiera colapsar los pipelines o CIs en falsos-positivos a raiz del mal servicio del entorno de terceros.

4. MANEJO NATIVO DE ARRAYS (LAMBDAS DE JAVASCRIPT)
   Hallazgo: Durante el Caso #4 (Consultar mascotas por Status 'sold'), fue necesario localizar una unica mascota precisa para validarla contra miles de resueltas dentro de una respuesta HTTP de tipo Array.
   Conclusion: El motor GraalVM que subyace en Karate permitio mitigar el uso de logica ciclica arcaica, solventado simplemente ejecutando un filter funcional avanzado sobre el response, limpiando enormemente el codigo y reforzando los principios de Clean Code del Ejercicio:
   * def foundPets = karate.filter(response, function(item){ return item.id == petId })
