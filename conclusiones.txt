============ HALLAZGOS Y CONCLUSIONES DEL EJERCICIO E2E DE PETSTORE ============

Analizando la arquitectura de pruebas mediante Karate DSL sobre la API pública de PetStore (Swagger), se establecen los siguientes hallazgos técnicos alineados al Ejercicio 2:

1. IDEMPOTENCIA Y COLISIONES DE DATOS (GENERACIÓN DE PET ID MÓVIL)
   Hallazgo: La API de Swagger es un entorno público. Al ejecutar la acción "Añadir una mascota", insertar IDs estáticos (ej: 12345) genera altas probabilidades de solapamiento con otros desarrolladores ensuciando los asserts.
   Conclusión: Para aislar la prueba dinámicamente, en lugar de usar variables "hardcodeadas", se implementó criptografía de tiempo en Karate (usando funciones embebidas de Java System.currentTimeMillis()). Esto crea IDs de 8 dígitos totalmente únicos en cada compilación (ej: "TestPet_1712..."), permitiendo que todo el ciclo se cumpla limpiamente sin miedo a falsos negativos por sobreescritura ajena.

2. ORQUESTACIÓN DEL ESTADO DEL CICLO E2E (AISLAMIENTO DE ESCENARIOS)
   Hallazgo: A diferencia de Cucumber nativo en Java donde se pueden instanciar variables globales para compartirse, Karate es muy estricto y vacía la memoria al cambiar de "Scenario". Intentar fragmentar las peticiones quebró las dependencias contextuales.
   Conclusión: El flujo entero (Crear -> Leer -> Actualizar -> Flitrar) debe resolverse y empaquetarse secuencialmente dentro de un solo escenario transaccional ("Idempotent E2E Lifecycle"). Recuperar un `petId` del `response` y reutilizarlo en la siguiente petición como `#(petId)` es la demostración técnica del manejo de estados maduro que requiere esta tecnología.

3. INESTABILIDAD Y RESILIENCIA DEL SERVIDOR PÚBLICO (BUGS 500 VS 404)
   Hallazgo: En validaciones asertivas usando números ficticios absurdos, el servidor público no está bien configurado y colapsaba arrojando "Exception Code 500 Internal Server Error" en lugar de un tradicional "404 Not Found" para búsquedas vacías.
   Conclusión: La aserción Gherkin fue diseñada explícitamente para sobreponerse a fallos de terceros implementando tolerancia. Al definir `Then match responseStatus == 404 || responseStatus == 500`, garantizamos que un comportamiento pobre externo de PetStore no bloquee engañosamente los pipelines CI/CD nuestros.

4. PREVENCIÓN DE NOTACIÓN CIENTÍFICA EN IDENTIFICADORES (GRAALVM)
   Hallazgo: Al generar números extremadamente grandes para IDs, el framework GraalVM subyacente de Karate los convertía de forma errónea a notación científica en las peticiones GET (ej. /pet/8.83E8), rebotando en un 404 legítimo.
   Conclusión: Se solventó inyectando polimorfismo desde Java forzando `java.lang.Integer.parseInt()` sobre la variable Javascript en el request, parseando forzosamente las variables a enteros convencionales.

5. MANEJO NATIVO AVANZADO DE ARRAYS
   Hallazgo: En el último caso solicitado ("Consultar mascota modificada por status sold"), Fetching por Status devolvía un array JSON masivo con miles de objetos, no uno solo, haciendo difícil encontrar la mascota puntual que actualizamos.
   Conclusión: Puesto que no podíamos iterar bucles primitivos arcaicos, se resolvió elegantemente aplicando Lambdas de Javascript habilitadas por el motor de Karate (`* def foundPets = karate.filter(response, function(item){ return item.id == petId })`), lo que demostró un dominio funcional total de la data extraída de la respuesta HTTP, consolidando el test en estado Passed.
